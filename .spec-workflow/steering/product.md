# Product Overview

## Product Purpose

OBD (Open Batch Processor) 是一个专门用于批量调用 Dify 工作流 API 的 Python 工具，旨在解决以下核心问题：

- **手动测试效率低**: 传统逐个测试 Dify 工作流耗时耗力
- **结果对比困难**: 缺乏自动化的答案验证和准确率评估机制
- **统计计算繁琐**: 手动计算测试指标（准确率、成功率等）容易出错
- **配置管理混乱**: 缺乏统一的配置管理和测试场景复用能力

核心目的：通过自动化批处理，将工作流测试效率提升 10 倍以上，同时提供可量化的测试结果评估体系。

## Target Users

### 主要用户

**内部开发者/QA 团队**是 OBD 的核心目标用户群体，他们使用该工具进行 Dify 工作流的开发和测试验证。

### 用户需求分析

1. **快速批量测试能力**
   - 需要在短时间内验证工作流对大量问题的处理能力
   - 希望避免重复的手动测试操作
   - 要求测试结果可追溯和复现

2. **自动化答案对比**
   - 需要灵活的答案匹配算法，适应不同类型的问题
   - 希望减少人工判定的主观性
   - 要求提供详细的匹配依据（匹配类型、相似度）

3. **量化测试结果**
   - 需要准确的统计指标（准确率、成功率、错误率）
   - 希望看到匹配类型的分布情况
   - 要求生成标准化的测试报告

4. **灵活的配置管理**
   - 需要支持不同的测试场景（工作流版本、匹配方法）
   - 希望配置简单且易于维护
   - 要求配置文件与敏感数据分离

## Key Features

### 1. Excel 批量导入
- 支持从 Excel/CSV 文件批量读取问题和标准答案
- 可配置的列名映射（question_column, answer_column）
- 支持指定处理范围（行索引范围）

### 2. Dify API 集成
- 完整封装 Dify 工作流 API 调用
- 支持云端和本地 Dify 部署
- 可配置的工作流版本（workflow_id）
- 灵活的超时和请求延迟设置

### 3. 多模式答案对比
- **exact**: 精确匹配（去除空格 + 转小写）
  - 适用场景：数字、代码、标准化答案
- **fuzzy**: 模糊匹配（使用 `difflib.SequenceMatcher`，相似度≥0.8）
  - 适用场景：表述相近但不完全相同的答案
- **keyword**: 关键词匹配（正则提取中文、英文、数字）
  - 适用场景：包含关键信息的长文本答案
- **auto**: 自动选择最佳匹配方式
  - 策略：按优先级尝试 exact → fuzzy → keyword
  - 推荐作为默认模式

### 4. 统计与分析
- 自动计算准确率（correct / total）
- 自动计算成功率（(total - failed) / total）
- 按匹配类型统计分布（exact/fuzzy/keyword）
- 错误分类（错误/失败/正确）

### 5. 结果导出
- 生成双 sheet 的 Excel 报告：
  - **Sheet 1**: 详细结果（问题、期望答案、实际答案、匹配类型、状态）
  - **Sheet 2**: 统计摘要（总数、准确率、成功率、匹配类型分布）
- 包含原始数据和处理后的对比信息
- 便于人工审核和归档

## Business Objectives

1. **提升工作流测试效率**
   - 目标：将单次测试时间从小时级降低到分钟级
   - 支持批量处理 10-1000 个问题

2. **实现自动化测试流程**
   - 目标：减少 90% 的人工干预操作
   - 从配置到结果生成全自动执行

3. **提供可量化的测试结果评估**
   - 目标：所有测试结果都可量化（准确率、成功率）
   - 提供详细的分类统计（按匹配类型、按错误类型）

4. **支持灵活的测试场景配置**
   - 目标：通过配置文件快速切换不同测试场景
   - 支持不同工作流版本、不同匹配算法的对比

## Success Metrics

### 核心性能指标

1. **处理性能**
   - **基准**: 每分钟处理 ≥ 60 个问题
   - **优化目标**: 每分钟处理 ≥ 100 个问题
   - **测量方法**: 实际运行时间统计

2. **答案匹配准确率**
   - **目标**: 对比算法误判率 < 5%
   - **测量方法**: 人工抽检 + 用户反馈
   - **优化方向**: 算法参数调优、新增匹配模式

3. **系统稳定性（可用性）**
   - **目标**:
     - 单次运行成功率 > 98%
     - 可支持 >1000 条数据连续处理
   - **测量方法**:
     - API 失败率统计
     - 长时间运行稳定性测试
   - **优化方向**: 重试机制、断点续传

4. **用户体验（易用性）**
   - **目标**:
     - 配置时间 < 5 分钟（首次使用）
     - 首次使用成功率 > 90%（零错误运行）
     - 错误信息清晰易懂
   - **测量方法**:
     - 新用户测试
     - 文档可读性评估
   - **优化方向**: 完善文档、改进错误提示

## Product Principles

### 1. 效率优先（Efficiency First）
- 自动化所有可以自动化的流程
- 减少重复操作和手动干预
- 批量处理优于单个处理

### 2. 灵活性（Flexibility）
- 支持多种匹配算法，适应不同问题类型
- 可配置的参数（超时、延迟、工作流版本）
- 支持多种输入/输出格式

### 3. 可靠性（Reliability）
- 完善的错误处理和降级机制
- 详细的日志记录和错误提示
- 失败场景的优雅处理

### 4. 可维护性（Maintainability）
- 模块化代码结构，便于扩展和修复
- 清晰的文档和配置示例
- 遵循最佳实践和设计模式

## Monitoring & Visibility

### 当前实现（CLI 模式）

- **Dashboard Type**: 命令行界面（CLI）
- **Real-time Updates**: 实时进度显示（逐行处理状态）
- **Key Metrics Displayed**:
  - 当前处理进度（已处理/总数）
  - 实时结果状态（正确/错误/失败）
  - 匹配类型（exact/fuzzy/keyword）
- **Sharing Capabilities**:
  - Excel 报告导出

## Future Vision

### Potential Enhancements

#### 1. 远程访问（Remote Access）
- **目的**: 允许团队成员远程监控测试进度
- **方案**: Tunnel 功能（如 ngrok）或云端部署
- **收益**: 提升团队协作效率，支持分布式测试

#### 2. 分析功能（Analytics）
- **历史趋势**:
  - 工作流准确率变化趋势
  - API 响应时间历史
  - 测试覆盖度分析
- **性能指标**:
  - 不同工作流版本的对比
  - 不同匹配算法的效果对比
  - 问题类型的准确率分布

#### 3. 协作功能（Collaboration）
- **多用户支持**:
  - 团队成员可同时使用
  - 基于角色的权限控制
- **注释和反馈**:
  - 对测试结果添加评论
  - 标记问题并指派负责人
- **版本控制**:
  - 测试结果版本管理
  - 支持 diff 对比

#### 4. 技术能力增强

**异步支持（asyncio）**:
- 使用 `aiohttp` 替代 `requests`
- 提升并发处理能力（3-10 倍）
- 支持并发数可配置

**重试机制（tenacity）**:
- 集成 `tenacity` 库实现自动重试
- 指数退避策略
- 最大重试次数可配置

**日志系统（logging）**:
- 实现结构化日志（JSON 格式）
- 分级日志（DEBUG/INFO/WARNING/ERROR）
- 日志轮转和归档

**插件化架构**:
- 支持自定义匹配算法（插件模式）
- 支持自定义输出格式（JSON/CSV/PDF）
- 支持自定义处理器（如调用外部 API）

**Dashboard 可视化**:
- Web 界面实时显示处理进度
- 可视化统计图表（准确率趋势、匹配类型分布）
- 支持交互式数据筛选和导出
